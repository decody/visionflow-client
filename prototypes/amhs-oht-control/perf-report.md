## 판정 (목표 10Hz, 예산 100ms/틱)

- **500대**: frame p95 1.37ms → ✅ 10Hz 지속 가능 (여유 73.17×)
- **1,000대**: frame p95 2ms → ✅ 10Hz 지속 가능 (여유 49.95×)
- **2,000대**: frame p95 3.58ms → ✅ 10Hz 지속 가능 (여유 27.93×)
- **5,000대**: frame p95 10.03ms → ✅ 10Hz 지속 가능 (여유 9.97×)

> 참고: 이 수치는 시뮬레이션 코어(계산+직렬화)만 측정한다. 브라우저 렌더 완료 지연은 앱 개발 진단 패널의 렌더 p95(postrender)로 별도 계측한다.
>
> OHT 가·감속·배터리 도입으로 매 틱 속도 변화 델타가 늘어(정속 주행 시 speed 델타 0 → 가속 구간 매 틱 변화) 5,000대 델타가 114.6→131.2KB(+14%), frame p95가 7.4→10.0ms로 상승했다. 여전히 100ms 예산 대비 ~10× 여유로 코어는 병목이 아니다.

## Chrome 통합 렌더 측정 (2026-09-19)

- 환경: Codex에서 연 전경 Chrome, Next.js 개발 서버, Worker 소스, 10Hz, FAB 전체가 보이는 Bay LOD
- 측정: fleet 변경 후 약 10초 안정화 시점의 앱 개발 진단 패널. JS heap은 Chrome `performance.memory.usedJSHeapSize`의 순간값으로 GC 시점에 따라 변동한다.

- 모든 규모에서 메시지 10Hz를 유지했고 재동기는 0회였으며 브라우저 오류·경고가 발생하지 않았다.
- 5,000대 지속 부하에서도 heap은 GC 후 235.5MB로 내려가 단기 누수 징후는 없었다.
- rAF 1 FPS와 약 1초의 postrender p95가 대수와 무관하게 거의 고정됐다. 기존 자동화 측정의 1~4 FPS 현상과 같아 이 수치는 자동화 Chrome의 프레임 제한 영향을 크게 받는다. 실제 사용자 Chrome의 GPU 렌더 한계로 해석할 수 없다.
- 따라서 이번 결과는 **데이터 수신·적용 안정성과 메모리 규모 검증**으로 사용한다. 출시 성능 판정에는 자동화가 없는 실제 사용자 전경 Chrome에서 같은 표를 다시 측정해야 한다.
