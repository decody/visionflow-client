# VisionFlow Client 분석 보고서

작성일: 2026-08-13  
분석 대상: `visionflow-client` 및 포트폴리오 연동에 관련된 `visionflow-server`  
분석 방법: Chrome MCP를 이용한 데스크톱·모바일 화면 검토, 주요 페이지 DOM 확인, 클라이언트와 Spring/PostgreSQL 연동 코드 점검

## 1. 요약

VisionFlow Client는 AI를 활용하는 디지털 스튜디오를 표방하며 Web 3D, 광고 이미지, 웹·앱, 데이터 대시보드 서비스를 제공한다. 전체적인 시각 품질과 서비스 설명의 구체성은 양호하지만, 현재 사업의 핵심인 **AI 기반 코딩 앱과 Web 3D 개발**이 네 가지 서비스 중 하나로 분산되어 전문성이 약하게 전달된다.

기술적으로는 Next.js BFF와 Spring Boot API, PostgreSQL을 연결하는 구조가 마련되어 있다. Work 페이지의 0건 표시는 포트폴리오 데이터가 아직 입력되지 않은 초기 상태이며, 서버에는 `works` 테이블과 공개·관리자 CRUD API가 구현되어 있다. 따라서 데이터 입력 후 포트폴리오 목록은 표시될 수 있다.

다만 실제 데이터를 입력하기 전에 Spring 응답과 클라이언트 모델의 필드명 차이, 공개 상태 관리 부재, 포트폴리오 상세 정보 부족, 빈 DB에서 샘플 사례가 실제 사례처럼 노출되는 문제를 해결해야 한다.

가장 높은 우선순위는 다음과 같다.

1. Work API의 camelCase/snake_case 계약 통일
2. 포트폴리오 공개 여부와 상세 사례 필드 확장
3. 홈의 샘플 실적과 DB 기반 실적의 일관성 확보
4. 서비스 페이지 히어로 잘림 및 모바일 내비게이션 수정
5. AI 제품 개발과 Web 3D 중심으로 포지셔닝 재정리

## 2. 현재 제품 구조

### 2.1 프런트엔드

- Next.js 16 기반 App Router
- React 및 TypeScript
- TanStack Query를 통한 서버 상태 관리
- Ant Design 및 AG Grid 기반 관리자 UI
- Next.js Route Handler를 BFF로 사용
- 공용 타입과 라우트를 workspace package로 분리
- Web 3D는 Three.js/react-three-fiber 계열 기술을 사용하는 구조

브라우저는 Spring 서버를 직접 호출하지 않고 동일 출처의 `/api/**` Route Handler를 호출한다. Route Handler가 `API_BASE_URL`의 Spring API로 요청을 전달한다.

```text
Browser
  -> Next.js UI / TanStack Query
  -> Next.js Route Handler (BFF)
  -> Spring Boot REST API
  -> MyBatis
  -> PostgreSQL
```

이 구조는 브라우저에 백엔드 주소와 인증 세부 구현을 노출하지 않고, 관리자 API용 단기 JWT를 BFF에서 발급할 수 있다는 장점이 있다.

### 2.2 포트폴리오 서버

`visionflow-server`에는 다음 구성이 존재한다.

- PostgreSQL 17
- Flyway 스키마 마이그레이션
- MyBatis SQL Mapper
- 공개 Work 조회 API
- 관리자 Work CRUD API
- Spring Security 기반 관리자 권한 검사

주요 API는 다음과 같다.

| 용도 | 메서드 및 경로 | 인증 |
|---|---|---|
| 포트폴리오 목록 | `GET /api/works` | 불필요 |
| 포트폴리오 상세 | `GET /api/works/{id}` | 불필요 |
| 관리자 목록 | `GET /api/admin/works` | Admin 이상 |
| 등록 | `POST /api/admin/works` | Admin 이상 |
| 수정 | `PUT /api/admin/works/{id}` | Admin 이상 |
| 삭제 | `DELETE /api/admin/works/{id}` | Admin 이상 |

현재 `works` 테이블은 다음 정보를 저장한다.

- `id`
- `title`
- `category`
- `industry`
- `size`
- `roles`
- `image`
- `link_label`
- `link_url`
- `is_important`
- `created_at`

## 3. 잘된 점

### 3.1 시각 디자인

- 흰색 헤더와 짙은 네이비 히어로의 대비가 명확하다.
- 큰 제목, 짧은 설명, CTA 순서가 분명해 첫 화면의 기본 정보 위계가 좋다.
- 파란색 CTA가 일관되게 사용되어 문의 동선을 쉽게 찾을 수 있다.
- 서비스별 카드, 가격, 기간, 산출물 표현이 구매자의 사전 판단을 돕는다.
- Web 3D 페이지에 직접 조작하는 컨피규레이터를 배치한 방향은 좋은 차별점이다.
- 한국어 본문에 Pretendard, 영문에 Inter를 적용하여 가독성이 안정적이다.

### 3.2 기획과 콘텐츠

- 서비스 범위와 최소 가격, 예상 기간을 공개해 상담 전 불확실성을 줄인다.
- 제작 프로세스와 단계별 산출물을 구체적으로 설명한다.
- 적합한 프로젝트와 적합하지 않은 프로젝트를 구분한 Fit Check는 리드를 선별하는 데 도움이 된다.
- 무료 상담, NDA, 응답 시간 등 문의 결정에 필요한 정보를 반복적으로 제공한다.

### 3.3 기술 구조

- 공개 API와 관리자 API의 권한 경계가 분리되어 있다.
- PostgreSQL 스키마를 Flyway로 관리한다.
- MyBatis에서 SQL이 명시적으로 관리되어 데이터 흐름을 추적하기 쉽다.
- 클라이언트가 Spring을 직접 호출하지 않고 BFF를 통과한다.
- 관리자 포트폴리오 등록·수정 화면과 React Query mutation 구조가 이미 준비되어 있다.

## 4. 핵심 기획 문제

### 4.1 핵심 포지셔닝이 분산됨

현재 홈에서는 다음 네 가지 서비스가 거의 동일한 비중으로 표시된다.

- Web 3D
- Ad Visuals
- Web & App
- Dashboard

이 구성은 종합 디지털 에이전시로는 자연스럽지만, 핵심 사업인 AI 기반 코딩 앱과 Web 3D 개발 전문성을 약하게 만든다. 특히 현재 AI 설명은 콘텐츠 생산 속도를 높이는 도구에 집중되어 있고, AI가 제품의 기능으로 동작하는 앱 개발 역량은 충분히 드러나지 않는다.

권장 서비스 체계는 다음과 같다.

1. **AI Product Development**
   - AI 에이전트
   - 생성형 업무 도구
   - 문서·데이터 자동화
   - 사내 AI 애플리케이션
2. **Web 3D Development**
   - 제품 컨피규레이터
   - 360도 뷰어
   - 가상 쇼룸
   - 인터랙티브 캠페인
3. 광고 이미지와 대시보드는 보조 역량 또는 사례 유형으로 배치

추천 히어로 메시지 예시는 다음과 같다.

> AI가 실제로 일하는 웹앱, 고객이 직접 만지는 Web 3D.
>
> 생성형 AI 기능 설계부터 제품 개발·배포까지, 3D 컨피규레이터와 인터랙티브 웹 경험까지 한 팀이 만듭니다.

### 4.2 포트폴리오가 기술 이력 중심으로 설계됨

Work 페이지는 `React`, `Vue`, `퍼블리싱`, `접근성`, `프론트엔드 개발` 필터를 중심으로 구성되어 있다. 이는 개인 개발자의 경력 검색에는 적합하지만 AI/Web 3D 스튜디오의 구매 고객이 프로젝트를 탐색하는 방식과는 다르다.

구매자는 기술보다 다음 기준을 먼저 찾는다.

- 어떤 문제를 해결했는가
- 어떤 산업과 제품인가
- 결과가 어떻게 달라졌는가
- 기간과 담당 범위는 무엇인가
- 실제로 동작하는 결과를 볼 수 있는가

따라서 필터를 `AI 앱`, `Web 3D`, `이커머스`, `업무 자동화`, `브랜드 경험`처럼 구매 목적 중심으로 변경하고, 각 상세 페이지를 문제-해결-성과 구조로 만드는 것이 적절하다.

### 4.3 홈 콘텐츠가 과도하게 김

홈에는 서비스, 차별점, 사례, 숫자, 프로세스, 고객사, 후기, FAQ, 최종 CTA가 모두 들어 있다. 각 섹션 자체는 타당하지만 연속해서 배치되어 핵심 메시지가 희석된다.

권장 핵심 흐름은 다음과 같다.

1. 핵심 가치 제안
2. 실제 작동하는 AI 앱/Web 3D 데모
3. 대표 사례 2~3건
4. 제공 서비스와 시작 가격
5. 진행 방식
6. 문의 CTA

후기, FAQ, 전체 기술 스택은 서비스 상세 페이지로 분산할 수 있다.

## 5. 화면 및 UX 문제

### 5.1 서비스 히어로의 왼쪽 잘림

Chrome 데스크톱 화면에서 `/web-3d`와 `/web-app` 히어로의 제목과 설명이 뷰포트 왼쪽에서 잘렸다. 장식용 배경의 음수 위치가 아니라 실제 콘텐츠 컨테이너 자체가 화면 밖으로 나간 상태로 보였다.

확인할 항목:

- 히어로 컨테이너의 너비와 `margin-inline`
- CSS Grid 컬럼의 최소 너비
- `left: -120px` 계열 장식 속성이 콘텐츠에도 영향을 주는지
- 1200px 전후 미디어 쿼리
- 브라우저 기본 배율과 가로 overflow

### 5.2 모바일 내비게이션

390x844 화면에서 메뉴가 햄버거 메뉴로 전환되지 않고 가로 스크롤 형태로 노출되었다. 로고, 메뉴, 견적 버튼이 세 줄을 차지해 콘텐츠가 시작되기 전 헤더 높이가 지나치게 커진다.

권장 방식:

- 모바일에서는 로고 + 견적 CTA + 메뉴 버튼 한 줄 구성
- 서비스 링크는 drawer 또는 sheet 안에 배치
- 현재 페이지와 주요 CTA를 메뉴 상단에 표시
- 가로 스크롤과 작은 좌우 이동 화살표 제거

### 5.3 Web 3D의 첫 시각적 증거가 약함

Web 3D 히어로의 문구는 “진짜 만질 수 있는 3D”이지만 첫 화면 오른쪽에는 정적인 와이어프레임 그래픽이 표시된다. 실제 컨피규레이터는 페이지 아래에 있어 핵심 주장과 증거가 떨어져 있다.

개선 방향:

- 히어로에 경량 실제 3D 모델 배치
- 드래그 회전 가능 여부를 즉시 표시
- 저사양 환경에는 영상 또는 이미지 폴백 제공
- 성능 수치는 실제 데모의 측정 결과와 연결

### 5.4 플로팅 UI 중복

오른쪽에 AI 캐릭터와 별도의 원형 플로팅 버튼이 함께 보이고, 개발 환경에서는 Next.js 및 TanStack Query 개발 도구도 화면에 노출된다. 여러 플로팅 요소가 CTA와 콘텐츠의 주의를 분산한다.

- 상담/AI 가이드 진입점을 하나로 통합
- 운영 빌드에서 개발 도구가 노출되지 않는지 확인
- 모바일에서는 플로팅 버튼 크기와 safe area 검증

## 6. Work 데이터 연동 분석

### 6.1 0건 상태의 의미

Work 페이지의 0건은 데이터베이스 연결 기능이 없어서가 아니다. 화면은 `/api/works`를 호출하고, Next.js Route Handler가 Spring의 `/api/works`로 전달한다. PostgreSQL `works` 테이블이 비어 있어 빈 배열이 반환된 상태다.

관리자 페이지 또는 SQL/Flyway seed를 통해 데이터를 입력하면 목록이 표시될 수 있다.

### 6.2 응답 계약 불일치

Spring `WorkResponse`는 다음과 같이 camelCase를 사용한다.

```ts
{
  createdAt: string;
  isImportant: boolean;
  linkLabel: string | null;
  linkUrl: string | null;
}
```

하지만 클라이언트의 `WorkRow`와 일부 화면 코드는 다음 snake_case 필드를 읽는다.

```ts
{
  created_at: string;
  is_important?: boolean;
  link_label?: string | null;
  link_url?: string | null;
}
```

현재 `apps/app/api/works/route.ts`는 `SpringWork[]`를 `WorkRow[]`로 변환하지 않고 그대로 반환한다. `normalizeWork`도 `roles`만 배열로 바꾼다. 따라서 실제 데이터를 넣으면 다음 문제가 발생할 수 있다.

- 연도가 `Recent`로 표시됨
- 링크 라벨과 링크 URL이 누락됨
- 중요 프로젝트 판별이 화면마다 달라짐
- 타입 선언과 런타임 데이터가 불일치함

해결 방법은 둘 중 하나를 선택해야 한다.

1. 클라이언트 전체를 Spring의 camelCase 계약으로 통일
2. BFF에서 `SpringWork`를 기존 `WorkRow` 형태로 명시적으로 변환

신규 Spring 중심 구조라면 첫 번째 방식을 권장한다. 임시 호환이 필요하다면 BFF 변환 함수를 한 곳에 두고 공개·관리자 응답에 공통 적용해야 한다.

### 6.3 공개 상태가 없음

현재 `works` 테이블에는 `is_published`가 없다. 공개 API는 모든 행을 반환하므로 관리자 작성 중인 데이터도 즉시 외부에 노출될 수 있다.

권장 사항:

- `is_published boolean not null default false`
- `published_at timestamptz`
- 공개 API에는 `is_published = true` 조건 적용
- 관리자 API에서는 전체 상태 조회
- 관리자 UI에 초안/공개 상태와 공개 일시 표시

### 6.4 사례 콘텐츠 필드가 부족함

현재 스키마는 목록 카드에는 사용할 수 있지만 상세 사례를 설득력 있게 구성하기에는 부족하다. 홈 샘플 카드가 보여주는 성과 지표도 DB에 저장할 공간이 없다.

권장 확장 필드:

| 필드 | 용도 |
|---|---|
| `slug` | 사람이 읽을 수 있는 상세 URL |
| `summary` | 목록 카드와 SEO 설명 |
| `client_name` | 고객명 또는 익명 표시명 |
| `project_year` | 실제 수행 연도 |
| `service_type` | AI Product, Web 3D 등 핵심 분류 |
| `metric_label` | 전환율, 처리 시간 등 성과 이름 |
| `metric_value` | `+47%`, `-60%` 등 값 |
| `challenge` | 고객 문제 |
| `solution` | 해결 방식 |
| `outcome` | 결과와 검증 방식 |
| `tech_stack` | 사용 기술 목록 |
| `gallery_images` | 상세 이미지 목록 |
| `is_published` | 공개 상태 |
| `display_order` | 운영자가 정하는 노출 순서 |

상세 콘텐츠가 길고 구조가 자주 바뀐다면 `case_study jsonb`를 사용하는 방법도 있지만, 검색과 집계가 필요한 핵심 속성은 일반 컬럼으로 유지하는 편이 좋다.

### 6.5 홈 플레이스홀더 정책

DB가 비어 있을 때 홈은 `PLACEHOLDER_WORKS`를 사용해 Nordic Furniture, 뷰티 브랜드 K, EdTech Startup, Fintech Co. 사례를 표시한다. Work 페이지는 빈 상태를 표시하므로 두 화면이 상충한다.

운영 정책을 명확히 해야 한다.

- 개발 환경에서만 플레이스홀더 표시
- 운영에서는 빈 상태 또는 “사례 준비 중” 표시
- 샘플을 유지한다면 카드에 `DEMO` 또는 `CONCEPT` 명시
- 실제 사례를 seed 데이터로 넣을 경우 사실 확인된 정보만 사용

### 6.6 통계 계산 의미

홈의 통계는 현재 다음 방식으로 계산된다.

- 누적 프로젝트: `works.length`
- 협력 고객사: 서로 다른 `industry` 값의 개수

산업군 개수와 협력 고객사 수는 의미가 다르다. `industry` 집계를 유지한다면 라벨을 `수행 산업군`으로 바꿔야 한다. 실제 고객사 수를 표시하려면 고객사 식별 필드 또는 별도 Client 테이블이 필요하다.

또한 페이지에 전달된 Work 목록만 세는 방식은 페이지네이션 도입 시 잘못된 통계를 만들 수 있다. 장기적으로는 서버의 집계 API를 사용하는 편이 안전하다.

## 7. 콘텐츠 신뢰성 점검

실제 DB를 채우면 0건 문제는 해소되지만, 다음 콘텐츠는 별도로 검증해야 한다.

- `120+ 프로젝트`, `80+ 고객사` 등 정적 숫자
- 전환율, CTR, 완강률, 운영 시간 개선 수치
- 고객사 로고와 후기
- `모바일 60fps 보장`
- `Lighthouse 90+ 인증`
- `자산 70% 감소`
- 문의 페이지의 주소와 전화번호 플레이스홀더

성과 수치는 측정 기간, 비교 기준, 대상 트래픽을 사례 상세에 함께 제시하는 것이 좋다. 공개할 수 없는 고객은 익명 처리하되 산업, 규모, 담당 범위, 결과 측정 방식은 설명해야 한다.

## 8. 메타데이터와 기술 표현

루트 metadata의 description은 현재 다음과 같다.

```text
VisionFlow realtime computer vision operations dashboard
```

실제 사이트는 AI 기반 디지털 스튜디오이므로 검색 결과와 공유 미리보기의 설명이 서비스와 맞지 않는다. Open Graph, Twitter card, canonical URL도 함께 점검해야 한다.

또한 화면에는 `Next.js 14`가 표시되지만 실제 프로젝트는 Next.js 16.2.4를 사용한다. 기술 버전을 마케팅 콘텐츠에 직접 표시하면 빠르게 낡아 보일 수 있으므로 다음과 같이 표현하는 편이 낫다.

- `Next.js App Router`
- `React/TypeScript 기반`
- 또는 실제 package version에서 자동 생성

일부 소스의 주석과 문자열이 콘솔에서 깨진 한글로 표시되었다. 파일 자체 인코딩 또는 터미널 코드페이지 문제인지 구분하고 저장소 전체를 UTF-8로 통일해야 한다.

## 9. 문의 전환 개선

현재 상단의 `무료 견적받기`는 `/contact`로 이동하고, 사용자는 다시 견적·제휴·일반 문의 중 하나를 선택한다. 견적 의도가 명확한 CTA이므로 `/contact/quote`로 직접 연결하는 것이 단계 수를 줄인다.

권장 견적 폼 구성:

1. AI 앱 또는 Web 3D 선택
2. 해결하려는 문제
3. 원하는 핵심 기능
4. 예산 범위
5. 희망 일정
6. 연락처

폼 옆에는 시작 가격, 예상 응답 시간, NDA 가능 여부, 제출 이후 절차를 표시한다.

## 11. 데이터 입력 후 검수 체크리스트

- [ ] 공개 Work API에 공개 상태인 데이터만 반환되는가
- [ ] 중요 프로젝트가 먼저 정렬되는가
- [ ] 생성일 또는 프로젝트 연도가 올바르게 표시되는가
- [ ] 카드 이미지가 없을 때 폴백이 자연스러운가
- [ ] 역할 문자열이 배열로 안정적으로 변환되는가
- [ ] 상세 링크가 올바르게 이동하는가
- [ ] 홈과 Work 페이지가 동일한 사례 정보를 보여주는가
- [ ] 프로젝트 수와 산업군 수가 실제 데이터와 일치하는가
- [ ] 모바일에서 긴 제목과 역할 목록이 레이아웃을 깨지 않는가
- [ ] 미공개 프로젝트가 검색 및 AI 가이드 결과에 포함되지 않는가
- [ ] 서버 장애 시 로딩·오류·재시도 UI가 구분되는가
- [ ] 샘플 데이터가 운영 화면에 실제 사례처럼 노출되지 않는가

## 12. 최종 평가

VisionFlow Client는 서비스 소개와 문의 기능을 갖춘 상당히 완성도 높은 기반을 가지고 있다. 특히 가격·기간·산출물을 구체적으로 보여주는 점과 Next.js BFF-Spring-PostgreSQL로 이어지는 관리 구조는 좋다.

현재 가장 큰 과제는 기능 부족이 아니라 **브랜드가 주장하는 전문성, DB에서 제공하는 증거, 화면에 표시되는 콘텐츠를 하나의 계약으로 맞추는 것**이다. 포트폴리오 스키마와 API 계약을 먼저 정리한 뒤 실제 데이터를 입력하고, AI 제품 개발과 Web 3D를 중심으로 첫 화면을 재구성하면 신뢰도와 문의 전환 가능성이 크게 높아질 것이다.
