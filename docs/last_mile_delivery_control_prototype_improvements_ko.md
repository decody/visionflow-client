## 1. 종합 평가

현재 프로토타입은 포트폴리오용 합성 배송 관제 시뮬레이션으로 높은 완성도를 갖추고 있다. 도로 그래프, 배차, ETA, 주문 생명주기, 알람, 이력 재생, 역할·감사 경계, WebSocket 모드, 5,000대 코어 벤치마크까지 구현되어 있다.

다음 보완의 핵심은 기능을 더 추가하는 것보다 다음 세 가지다.

1. 실제 브라우저에서 렌더링과 상호작용을 검증한다.
2. 데모용 권한·실시간 경계를 운영 시스템에 가까운 계약으로 강화한다.
3. 대규모 실시간 데이터 전송량과 다중 클라이언트 상태를 정리한다.

### 진행 상태

- ✅ 운영 조치 2단계 확인 UI: 재배차·라이더 연락·특급 승격에 실행 전 확인 단계 추가
- ✅ 타입체크 및 프로덕션 빌드 검증
- ✅ 전체 unit test 69개 통과
- ✅ WebSocket 모드 브라우저 검증: 지도·도로·라이더·신호·허브 슬롯·도킹·추적선 확인
- ✅ 운영 조치 확인 UI 브라우저 검증: 확인 실행·취소 흐름 확인
- ✅ 네트워크 주소의 Web Worker 모드: Next 개발 서버 `allowedDevOrigins` 설정과 Worker 미지원 환경의 inline fallback을 추가해 `100.103.138.8:3013/?src=worker`에서도 40대 라이더·지도·도킹 상태가 표시됨을 확인
- ✅ WebSocket/Worker 명령 runtime validation: `count`, `rateHz`, `rule`, `scenario`, `riderId`, `orderId`, `alertId` payload 검증 및 잘못된 명령 거부
- ✅ WebSocket 서버 malformed JSON·잘못된 role·잘못된 focus 입력 거부
- ✅ 서버 인증 기반 역할 모델: `WS_AUTH_TOKENS` 기반 actor 도출, 인증 연결의 role 변경 거부
- ✅ delta 전송량 축소: 변경된 라이더만 `upd`에 포함하고 정지·충전 상태의 반복 전송 방지
- ✅ Playwright E2E 자동화: 핵심 렌더링·운영 조치 preview/cancel 2개 시나리오 통과
- ✅ 운영 보호 경계: WebSocket payload 상한·연결별 명령 rate limit·도메인 참조 ID 검증·선택적 JSONL 감사 로그
- ✅ 인증·참조 검증 회귀 테스트: unit test 70개 통과
- ✅ 세션별 엔진 분리 선택 모드: `WS_STATE_SCOPE=isolated`
- ✅ 연결별 권역/extent 구독 및 outbound 메시지 필터링
- ✅ HS256 JWT 최소 검증 경계: `WS_JWT_SECRET` 및 `sub/role/exp` claim
- ✅ 운영 KPI 확장: 완료·실패·SLA 준수율·평균 대기·배터리 위험·재배차 집계
- ⏳ 중앙 감사 로그 저장소와 실제 IdP/JWKS 교체는 배포 연동 단계의 후속 작업

## 2. 우선순위별 보완 항목

### P0 — 먼저 보완할 항목

#### 2.1 실제 브라우저 렌더 검증

Playwright smoke test와 실제 브라우저 검증으로 핵심 렌더링·상호작용은 확인했다. 다음 항목은 대규모 함대 회귀 범위를 넓힐 때 추가할 수 있다.

- Overview Heatmap 표시와 줌 전환
- Zone WebGL 포인트 렌더링
- Detail 방향 심벌·라벨·선택 오버레이
- 신호등과 도로 통제 레이어
- 도킹 단계와 허브 슬롯 라벨
- 5,000대에서 실제 FPS와 입력 반응성

추가 권장 작업:

- Playwright 기반 페이지 smoke test 추가
- 40/500/5,000대별 화면 캡처 검증
- Overview → Zone → Detail 줌 전환 테스트
- 라이더 선택·권역 필터·알람 포커스의 UI 회귀 테스트

#### 2.2 운영 조치의 2단계 확인

재배차·라이더 연락·특급 승격에 2단계 확인 UI를 추가해 대상·영향·실행 주체를 확인한 뒤 명령을 전송하도록 보완했다.

확인 화면에는 다음을 표시하는 것이 좋다.

- 대상 라이더·주문
- 현재 상태와 현재 ETA
- 실행 후 예상 영향
- 영향 받는 주문 수
- 실행 주체와 권한
- 최종 확인·취소 버튼

관련 코드: `src/app/page.tsx`의 `requestReassign`, `contactCourier`, `promoteExpress`

#### 2.3 권한 모델을 데모 수준에서 분리

기본 로컬 데모는 supervisor로 시작하지만, `WS_AUTH_TOKENS`가 설정된 연결은 URL token에서 actor를 서버가 도출하고 `setRole`을 거부한다. 따라서 데모 호환성과 인증 경계를 분리했다.

운영 시스템에 연결할 때는 다음을 적용해야 한다.

- JWT 또는 세션에서 actor를 서버가 도출
- 클라이언트의 `setRole` 제거
- 명령별 scope/site/tenant 권한 확인
- 승인·거부 감사 로그 서버 저장
- 연결별 rate limit과 명령 빈도 제한

현재 구현에서는 토큰 기반 actor 도출, 인증 세션의 role 변경 거부, 연결별 명령 빈도 제한, 선택적 JSONL 감사 로그까지 반영했다. JWT 검증·tenant/site scope·중앙 로그 저장은 실제 플랫폼 연동 시 교체할 경계다.

## 3. 실시간·성능 보완

### 3.1 델타 전송량 축소

최근 벤치마크 기준 5,000대에서 델타 평균은 약 928KB/틱이다. 10Hz로 전송하면 클라이언트 하나당 약 9.3MB/s가 될 수 있어, 실제 운영 단계에서는 viewport 구독·압축·바이너리 프로토콜을 추가 검토해야 한다.

현재 대부분의 이동 라이더가 매 틱 변경되므로 `upd/tick`은 여전히 큰 편이다. 다음 개선이 후속 과제다.

- 위치·상태가 변경된 라이더만 전송
- 권역·viewport별 구독 지원
- 라이더 ID 정수 압축
- MessagePack 또는 바이너리 프로토콜 검토
- WebSocket per-message compression 검토
- 중요도별 update rate 적용
- 다중 클라이언트의 동일 메시지 재직렬화 방지

현재 `perf-report.md`의 수치는 시뮬레이션 코어와 JSON 직렬화 중심이며 Playwright는 핵심 smoke test만 포함한다. 실제 네트워크 전송·브라우저 렌더를 포함한 장시간 성능 지표는 후속 과제다.

### 3.2 다중 클라이언트 상태 정책 정리

`server/ws-server.ts`는 모든 클라이언트가 하나의 `SimEngine`, `count`, `running`, `rateHz`를 공유한다.

따라서 한 클라이언트의 조작이 모든 클라이언트에 영향을 준다.

- 함대 규모 변경
- 시뮬레이션 일시정지·재개
- 시나리오 주입
- 배차 규칙 변경

현재는 README에 데모용 전역 시뮬레이션임을 명시했다. 실제 운영 전에는 다음 중 하나를 선택해야 한다.

- 데모용 전역 시뮬레이션임을 문서화
- 세션별 엔진 분리
- 공유 상태와 개인 상태를 구분
- 운영 조작은 승인된 사용자만 수행하고 다른 사용자는 read-only로 유지

현재 연결별로 payload 64KB, 10초당 기본 60개 명령 제한을 적용한다. `WS_STATE_SCOPE=isolated`에서는 연결별 엔진·일시정지·함대 규모를 분리하고, 기본 `shared`에서는 데모 상태를 공유한다. 중앙 게이트웨이의 tenant·사용자별 quota와 중앙 세션 저장소 연동은 배포 단계에서 확장해야 한다.

### 3.3 실시간 입력 스키마 검증

WebSocket 서버는 JSON 파싱 후 명령별 런타임 계약을 검증하고, 범위·허용값·필수 식별자를 통과한 명령만 처리한다. 최대 payload 크기와 도메인 객체 존재 여부는 후속 강화 항목이다.

명령별로 다음을 검증해야 한다.

- `type`
- `count`, `rateHz` 범위
- `scenario`, `rule`, `role` 허용값
- `riderId`, `orderId`, `alertId` 형식과 존재 여부
- 명령별 필수 필드
- 최대 payload 크기

현재 계약 검증은 의존성 없는 수동 파서로 구현했다. 스키마가 커지면 Zod 같은 런타임 스키마로 교체하는 것을 권장한다.

현재는 대상 rider/order/alert의 존재 여부와 payload 크기도 서버에서 확인한다. 도메인 상태가 여러 인스턴스로 분리되면 참조 검증은 해당 세션 또는 tenant 저장소를 기준으로 수행해야 한다.

### 4.2 알람 상태 모델 통일

정적 `DeliveryAlert` 타입에는 `MITIGATING`이 존재하지만, 실시간 `AlertStatus`는 `OPEN`, `ACKNOWLEDGED`, `RESOLVED`만 사용한다.

기획 의도에 맞추려면 다음 상태 흐름을 일관되게 정의해야 한다.

`OPEN → ACKNOWLEDGED → MITIGATING → RESOLVED`

반대로 `MITIGATING`을 사용하지 않을 경우에는 정적 타입과 기획 문서에서 제거해 모델을 하나로 통일해야 한다.

### 4.3 라이더 상세 정보 보강

현재 상세 패널은 현재 주문, ETA, 배터리, 좌표 중심이다. 운영 판단을 위해 다음 정보를 추가할 수 있다.

## 8. 검증 메모

진행 문서에는 타입체크, 67개 unit test, 프로덕션 빌드, 개발 서버 200 응답, 5,000대 코어 성능 벤치 통과가 기록되어 있다.

이번 분석에서 동일 명령을 재실행했을 때는 pnpm 프로세스가 출력 없이 정지해 독립적인 재검증을 완료하지 못했다. 실행 과정에서 자동 변경된 `next-env.d.ts`는 원상 복구했다.

따라서 최종 완료 판정 전에는 의존성 설치 상태와 실행 환경을 정리한 뒤 typecheck·unit test·build·브라우저 smoke test를 다시 수행해야 한다.
